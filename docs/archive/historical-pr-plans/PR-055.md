# PR-055: Provider-Neutral Tool Result Contract

## Goal
Establish a strict provider-neutral external tool-result envelope before any tool output can be normalized into Protocol DomainData.

## Scope
- Turn `packages/tool-bridge` from placeholder into a package depending only on `protocol`.
- Add versioned `ExternalToolResult` contract.
- Require semantic tool identity (`kind`, `name`) rather than endpoint/provider implementation data.
- Support explicit outcomes: `success`, `partial`, `empty`, `failure`.
- Enforce outcome/data/failure consistency.
- Accept bounded canonical JSON payload only through Protocol `parseJsonValue`.
- Add optional canonical freshness metadata.
- Reject unknown fields, accessors/getters, functions, symbols, circular data, raw URL/token/call-id/message/stack fields.
- Return detached deep-frozen normalized values.
- Add tests and documentation.

## Out of scope
- OpenAI/LangChain/MCP-specific parsing.
- DomainData mapping.
- retry logic.
- tool execution.
- network calls.
- raw exception/message preservation.

## Acceptance criteria
- Tool Bridge depends internally only on Protocol.
- input getters/accessors are never executed.
- success/partial require data; failure requires a semantic failure code; empty carries neither data nor failure.
- raw implementation/credential/error-message fields fail as unknown fields.
- output is detached from caller mutation and deeply frozen.
- no opaque external call IDs or endpoints enter the canonical envelope.

## RE/QC focus
Look for provider coupling, credential/endpoint leakage, raw exception text, accessor execution, unbounded/unvalidated JSON, outcome ambiguity, caller-reference retention, mutable normalized data, tool execution, or Runtime Web dependencies.
