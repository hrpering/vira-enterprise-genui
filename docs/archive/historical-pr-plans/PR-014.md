# PR-014: Runtime permissions

## Goal
Add deterministic default-deny permission decisions for semantic runtime actions and capabilities without introducing executable policy code or trusting action provenance.

## Scope
- Define versioned immutable permission policy data.
- Support exact action/capability rules with `allow`, `deny`, and `confirm` effects.
- Default unmatched subjects to deny.
- Reject duplicate rules, wildcards, conditions, callbacks, and unknown fields.
- Ensure action `source` is not authorization evidence.
- Add action/capability evaluation helpers, tests, and documentation.

## Out of scope
- User/role authentication.
- Confirmation UX or confirmation token issuance.
- Backend execution.
- Runtime reducer wiring.
- Adapter/customer policy mapping.
- Wildcards, expressions, predicates, or policy scripting.

## Acceptance criteria
- Unmatched actions/capabilities deterministically deny.
- Exact rules deterministically return allow/deny/confirm.
- `confirm` is never represented as allow.
- `user`, `host`, and `system` action sources have no implicit privilege.
- Duplicate/wildcard/executable/conditional policy shapes are rejected.
- Policies and decisions are immutable data.
- No network/framework/host side effects exist.

## RE/QC focus
Look for fail-open defaults, source-based privilege escalation, wildcard ambiguity, callback/expression execution, duplicate-rule precedence, confirm-as-allow bugs, hidden role/customer coupling, mutable policy data, or permission checks embedded into low-level patch/lifecycle primitives.
