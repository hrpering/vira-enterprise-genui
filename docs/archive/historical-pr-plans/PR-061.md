# PR-061: Plain-Text Content Security Boundary

## Goal
Establish the MVP content-security invariant that untrusted/generated strings are authorized only for a plain-text sink; raw HTML/SVG/MathML sinks are not part of the security surface.

## OSS reference
DOMPurify is a mature DOM sanitizer for HTML/MathML/SVG and demonstrates why HTML sanitization is its own specialized security problem. Vira deliberately avoids opening that problem in the MVP renderer: no sanitizer dependency is added and no sanitized-HTML capability is introduced.

## Scope
- Turn `packages/security` into a real dependency-free package.
- Add immutable `PlainTextContent` values explicitly scoped to the `plain-text` sink.
- Add a bounded text length guard.
- Add explicit sink authorization where only `plain-text` is accepted.
- Preserve markup-looking text literally rather than pretending it is safe HTML.
- Add tests and documentation.

## Explicitly out of scope
- HTML sanitization.
- `innerHTML` / `outerHTML` / `insertAdjacentHTML` authorization.
- TrustedHTML / Trusted Types policy creation.
- Markdown-to-HTML rendering.
- DOMPurify or other sanitizer runtime dependency.
- URL/style/script sinks.

## Acceptance criteria
- Security package has no internal or third-party dependencies.
- `<script>`, HTML entities, and markup-looking user text remain unchanged as plain text.
- the only authorized content sink is `plain-text`.
- requests for `html`, `svg`, `mathml`, `script`, `style`, or arbitrary sink names fail closed.
- oversized text fails deterministically.
- public naming remains sink-scoped; no API claims a value is generically safe for HTML.

## RE/QC focus
Look for sanitized-HTML claims, hidden HTML parsing, markup stripping/rewriting, permissive sink fallback, third-party runtime dependencies, DOM coupling, globally-safe string naming, or APIs that could be passed to innerHTML by implication.
