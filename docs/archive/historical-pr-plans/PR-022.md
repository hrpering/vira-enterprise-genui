# PR-022: Semantic Regions

## Goal
Define Composer's semantic capability-region contract without introducing layout, rendering, component, action, or brand ownership.

## Scope
- Define `primary`, `supporting`, and `deferred` semantic region roles.
- Define strict non-empty regions with semantic IDs and canonical capabilities.
- Preserve explicit region/capability order.
- Reject duplicate region IDs and duplicate capability identities across regions.
- Bound region count and total capability count before recursive parsing.
- Return recursively frozen canonical data.
- Add Composer package public/dependency surface, tests, and documentation.

## Out of scope
- Layout families/geometry.
- Disclosure/visibility policy.
- Components/brand adapters.
- Runtime actions/permissions.
- Data bindings.
- DOM/CSS/responsive behavior.

## Acceptance criteria
- Semantic regions remain priority groups rather than visual slots.
- Presentation/execution fields are rejected.
- Empty/invalid regions and duplicate semantic positions fail closed.
- Total capability count reuses Protocol's canonical ExperiencePlan limit.
- Accessor-backed/oversized input is rejected without unnecessary deep parsing.
- Output is immutable and serializable.

## RE/QC focus
Look for visual/layout leakage, component/action ownership, invented unowned region concepts, duplicate capability positions, fail-open empty regions, resource-limit gaps, mutable outputs, or Protocol limit duplication.
