# PR-059: LangChainJS ToolMessage Adapter

## Goal
Normalize LangChainJS `ToolMessage`-compatible values into Vira's provider-neutral `ExternalToolResult` without adding a LangChain runtime dependency or treating model-facing message content as structured GenUI data.

## OSS reference
The current LangChainJS `ToolMessage` contract distinguishes `content` from optional `artifact`, where `artifact` is the tool execution artifact not meant to be sent to the model, and exposes optional `status: "success" | "error"`. Vira uses that separation as an interoperability pattern rather than importing LangChain.

## Scope
- Add `normalizeLangChainToolMessage(toolName, message)`.
- Accept class-instance-compatible objects by reading known own data properties through descriptors.
- Never invoke accessor/getter properties.
- Require caller-supplied canonical semantic tool name; ignore opaque `tool_call_id`.
- Treat missing `status` as success for backwards compatibility with ToolMessage's optional status.
- Map `status: error` to `langchain.tool.error` without reading/copying artifact, content, metadata, IDs, or error text.
- For success, prefer canonical JSON `artifact` as structured tool data.
- Without artifact, map empty string/empty content array to canonical `empty`.
- Reject non-empty content-only success as `UNSTRUCTURED_RESULT` rather than parsing model-facing text into JSON.
- Revalidate constructed output through `parseExternalToolResult`.
- Add tests and documentation.

## Explicitly out of scope
- LangChain package dependency.
- LangGraph/agent execution.
- parsing ToolMessage text as JSON.
- copying metadata/tool_call_id into canonical data.
- transforming LangChain content blocks.
- retry/network behavior.

## Acceptance criteria
- Tool Bridge still depends internally only on Protocol.
- live class-like objects with ordinary own fields can be normalized.
- getter/accessor fields are never invoked.
- error messages/artifacts cannot leak into canonical failure.
- structured success uses artifact, not model-facing content.
- content-only non-empty results fail explicitly.
- final successful output passes the canonical ExternalToolResult parser.

## RE/QC focus
Look for LangChain package imports, getter invocation, tool_call_id leakage, raw error/content propagation, text-to-JSON parsing, content preferred over artifact, hidden execution, or provider fields escaping into canonical output.
