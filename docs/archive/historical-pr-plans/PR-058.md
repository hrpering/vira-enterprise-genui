# PR-058: MCP CallToolResult Adapter

## Goal
Normalize the current MCP `CallToolResult` shape into Vira's provider-neutral `ExternalToolResult` without taking a runtime dependency on the MCP SDK or leaking MCP transport/error details into canonical data.

## OSS reference
The adapter is informed by the official Model Context Protocol TypeScript SDK contract: tool results expose required `content`, optional object `structuredContent`, and optional `isError` where tool-level failures are represented inside the result. Vira uses those semantics as an interoperability reference, not as a package dependency or copied implementation.

## Scope
- Add `normalizeMcpCallToolResult(toolName, result)` under Tool Bridge provider adapters.
- Require caller-supplied canonical semantic tool identity because MCP `CallToolResult` itself does not own the tool name.
- Require MCP `content` to be an array as the structural result gate.
- Map `structuredContent` object to canonical success data.
- Map `isError: true` to canonical failure code `mcp.tool.error` without copying error text/content.
- Map successful empty `content` with no structured data to canonical `empty`.
- Reject non-empty unstructured-only success as `UNSTRUCTURED_RESULT` rather than inventing DomainData-ready JSON.
- Ignore MCP `_meta`/extension fields after getter-safe canonical JSON validation.
- Validate the constructed output again through `parseExternalToolResult`.
- Add tests and documentation.

## Explicitly out of scope
- MCP client/server execution or transport.
- MCP SDK package dependency.
- parsing text content into JSON.
- image/audio/resource rendering.
- copying MCP error content into canonical failure metadata.
- tool discovery/listing.
- retry/network behavior.

## Acceptance criteria
- Tool Bridge still depends internally only on Protocol.
- MCP SDK is not added to package dependencies.
- structured success produces canonical detached/frozen ExternalToolResult.
- error results never leak raw MCP content/metadata into canonical failure.
- text-only success fails explicitly rather than masquerading as empty or structured data.
- unknown MCP extension fields are ignored, not propagated.
- malformed/accessor-backed input fails closed.

## RE/QC focus
Look for MCP SDK coupling, raw error leakage, transport/call IDs, parsing untrusted text as JSON, provider fields escaping into canonical output, treating unstructured data as empty, hidden tool execution, or bypass of the provider-neutral result validator.
