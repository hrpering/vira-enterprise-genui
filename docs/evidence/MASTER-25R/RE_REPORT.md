### Canonical RC composition

`tooling/verify-enterprise-rc.mjs` executes the following fail-fast chain:

```text
repository + browser
  ↓
portable native conformance
  ↓
iOS Simulator
  ↓
Android Emulator
  ↓
external brand proof evidence
  ↓
Enterprise RC PASS
```

The script exits on the first command that cannot start or returns non-zero.

### External evidence boundary

`tooling/verify-external-brand-proof-evidence.mjs` is generic and domain-neutral. It requires:

- evidence version `1`;
- exact 40-character `viraHead`;
- exact Pack id/version/sha256 digest;
- exact platform set: Web, iOS, Android;
- each platform `passed: true` plus bounded trace reference;
- complete required gate set;
- `git rev-parse HEAD === evidence.viraHead`.

The required gate set includes same-Pack identity, Action Boundary, governance/approval, observability/ledger, cross-platform conformance, accessibility/localization, cross-tenant denial, wrong-Pack-version denial, unknown-component denial, unknown-action denial, unsigned-artifact denial, stale-revision denial, duplicate-retry denial and verified reconnect/cache behavior.

## Findings

1. MASTER-25 executable implementation is already sufficient for release closure; no duplicate release subsystem should be added.
2. Exact-head external evidence is intentionally the final release dependency and currently remains unbound to the post-CLEAN-00 tree.
3. The external verifier already prevents stale evidence from another Vira head.
4. The generic verifier does not contain Pegasus-specific branching and must remain generic.
5. `docs/pr-plans/ACTIVE_PHASE.md` and `MASTER_PLAN.md` were stale immediately after CLEAN-00 merged; they still represented CLEAN-00 as active and MASTER-25R as future.
6. The connected GitHub account exposes no separate Pegasus proof repository. The proof may exist only in another/local repository; its evidence cannot be inferred or fabricated from core.
7. Because external evidence binds to the executable Git HEAD, documentation/evidence commits made after a green RC execution cannot be treated as the same executable proof without an explicit final-diff argument. MASTER-25R therefore separates the executable-tree RC run from evidence-only closure commits and requires final Q8 confirmation that no executable content changed afterward.
8. A second-pass test-tree audit found no focused regression test for the two release scripts themselves. The broader MVP/runtime suite exercises many underlying contracts, but did not directly prove external-evidence exact-head rejection or the RC orchestrator's stage order/fail-fast/PASS-only-after-all-stages behavior.

## Gap closure

`tests/contract/enterprise-rc-gate.test.ts` was added as a black-box contract test without modifying either release script. It covers:

- valid evidence bound to the current test-repository HEAD;
- missing evidence;
- malformed JSON;
- stale `viraHead`;
- omitted required gate;
- failed platform proof;
- canonical RC stage order;
- first-failure short circuit;
- no RC PASS message after a failed stage.

The tests invoke the existing `.mjs` release scripts as child processes and therefore protect public release behavior rather than mirroring internal helper implementation.

A separate local behavioral harness using the same script boundaries confirmed valid exact-head evidence acceptance, five-stage canonical order and fail-fast exit/no-PASS behavior. That harness was executed under the available analysis environment and is only a sanity check; it is not Q7 release evidence and does not replace the repository's Node >=24/Vitest/native exact-head run.

## Authority decision

MASTER-25R owns release evidence closure only. The existing root/tooling RC gate remains canonical executable authority.

## Minimal-diff decision

The only justified executable addition is focused release-contract regression coverage. No package/runtime/SDK/tooling implementation change or dependency edge is required.

Current implementation scope is therefore:

- MASTER-25R phase/status reconciliation;
- reverse-engineering/verification evidence;
- one focused black-box release-gate test file.
