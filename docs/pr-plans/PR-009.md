# PR-009: Protocol versioning and compatibility policy

## Goal
Make protocol compatibility explicit and centrally inspectable without introducing negotiation, transport, or migration behavior.

## Scope
- Define the canonical list of protocol kinds.
- Expose immutable supported-version lists derived from each owning protocol constant.
- Add exact-match support checks.
- Document compatibility, evolution, and no-silent-downgrade rules.
- Add contract tests that keep the registry aligned with owning protocol constants.

## Out of scope
- Network version negotiation.
- Automatic migrations or downgrade/upgrade transforms.
- Supporting multiple historical versions before such versions exist.
- Runtime feature flags.
- Customer-specific compatibility shims.

## Allowed files
- `packages/protocol/src/versioning.ts`
- `packages/protocol/src/index.ts`
- `tests/contract/versioning.test.ts`
- `docs/protocol/versioning.md`
- `docs/pr-plans/PR-009.md`

## Acceptance criteria
- Every current top-level protocol kind appears exactly once in the central registry.
- Registry versions come from each protocol's owning version constant; version strings are not duplicated as independent literals.
- Returned supported-version collections are immutable.
- Support checks require exact string matches; numbers and unknown versions are rejected.
- Documentation states that parsers never silently coerce, upgrade, downgrade, or ignore unsupported versions.
- No transport, network, migration, planner, runtime, or renderer behavior is introduced.

## RE/QC focus
Confirm this PR creates one compatibility view rather than a second source of truth. Look for duplicated version literals, mutable registries, silent coercion, implied forward compatibility, transport negotiation, or migration behavior that belongs elsewhere.
