# PR-074: Reflection Boundary Hardening

## Goal
Close hostile JavaScript reflection/proxy escape paths discovered during final MVP reverse-engineering review without changing normal product or authorization semantics.

## Scope
- Harden Protocol canonical JSON and data-object inspection so hostile/revoked Proxies become validation failures.
- Harden Planner, Composer, and Runtime Web root data-object boundaries.
- Bound trusted Web SDK prototype traversal, detect cycles, and contain descriptor/prototype traps for DOM/id-factory methods.
- Contain hostile reflection traps in capability/component allowlists and network policy/request parsing.
- Contain LangChain ToolMessage own-property reflection traps without removing class-instance compatibility.
- Contain Telemetry event/exporter reflection traps and bound exporter prototype traversal.
- Contain injected Web Component platform/registry failures during registration.
- Preserve existing exact allowlist, network, tool normalization, telemetry, registration, and trusted-port semantics for ordinary inputs.
- Add adversarial regression tests proving proxy/provider exception text is not leaked.

## Out of scope
- New authorization semantics or policy features.
- New Planner/Composer behavior.
- New Protocol schema fields.
- Runtime Core state/reducer behavior changes.
- Network execution.
- Dynamic code, arbitrary HTML, iframe, or provider execution.
- Message queues, retries, background workers, or new dependencies.

## Acceptance criteria
- Hostile and revoked Proxy traps cannot escape public parsing/configuration/normalization APIs as raw exceptions.
- Trusted method lookup cannot loop indefinitely through a cyclic prototype graph.
- Existing getter-backed/accessor rejection remains intact.
- Failure messages remain generic and do not contain attacker/provider exception text.
- Protocol canonicalization still owns JSON normalization for downstream packages.
- No normal successful behavior, authorization decision, tool semantics, or telemetry semantics change.

## RE/QC focus
Look for reflection calls outside containment, prototype traversal without cycle/depth bounds, leaked exception text, semantic widening of allowlists/network policy, accidental trusted method execution during configuration, or broad catch blocks that swallow normal runtime effects rather than hostile input inspection.
