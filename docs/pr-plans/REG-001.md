# REG-001 — Experience Registry v1

## Status

Planned from authoritative `main` `5266db3e56f4c3e2de4a91f3dcb70e3108dbd2d4`.

Branch: `feat/experience-registry-v1`.

This work is independent from open Observability, Policy Engine and Protocol Gateway PRs. Before the final all-phase CI gate it must be reconciled onto the then-latest authoritative main.

## Reverse-engineering baseline

`@vira-enterprise-genui/experience-packs` already owns the canonical distribution manifest:

- `id` and release-semver `version`;
- publisher identity/name;
- human metadata/tags;
- Vira compatibility range;
- entrypoints;
- content-addressed artifact descriptors;
- canonical fail-closed `parseExperiencePackManifest()`;
- deterministic `serializeExperiencePackManifest()`.

Registry must not create a second Pack schema, artifact descriptor model, publisher model, compatibility model, or media type.

## Goal

Add a bounded, provider-neutral, persistence-free Registry snapshot contract over canonical Experience Pack manifests.

```text
bounded Registry JSON text
      ↓
JSON.parse()
      ↓
iterative null-prototype detach
      ↓
existing parseExperiencePackManifest()
      ↓
canonical Pack manifests
      ↓
identity-marked Experience Registry snapshot
      ↓
exact primitive id + version lookup
```

## V1 scope

- immutable versioned snapshot;
- maximum 256 manifests per snapshot;
- every manifest validated by the existing Experience Packs parser;
- duplicate `(id, version)` pairs rejected;
- deterministic ordering by exact `id`, then exact `version` string;
- exact lookup by primitive `id + version` only;
- lookup returns the canonical `ExperiencePackManifest` or `null` when absent.

V1 intentionally has no `latest`, semver-range resolution, channels, aliases, mutable lifecycle state, ranking, popularity, download counts, installation state, persistence, remote fetch, authentication, or marketplace semantics.

## Review-driven untrusted-data boundary

Initial review found that a reflective object-graph preflight could not honestly guarantee no Proxy trap execution: any generic JavaScript reflection can itself hit Proxy traps. The same design also allowed large flat property sets to force enumeration work before the advertised node budget and mirrored current Pack id/version maximum lengths in Registry lookup constants.

A follow-up review also identified inherited-state risk: even ordinary JSON objects inherit from `Object.prototype`, while the existing Pack parser performs some direct property reads. In a prototype-polluted environment a missing Pack key could otherwise hit an inherited getter.

REG-001 therefore uses a stronger boundary:

- untrusted snapshot input must be JSON text;
- input text length is capped at 16,000,000 characters before parsing;
- `JSON.parse()` removes Proxy/accessor/symbol/custom-array input state;
- the parsed graph is iteratively detached so every JSON object has a null prototype before Pack validation;
- Pack semantics are then delegated exclusively to `parseExperiencePackManifest()`;
- successful snapshot objects are recorded in a module-private `WeakSet`;
- exact lookup accepts only one of those canonical snapshot identities and primitive id/version strings;
- lookup uses one independent 4,096-character safety bound rather than reproducing Pack grammar maxima.

This removes the reflective preflight entirely instead of trying to detect Proxies in a cross-runtime package, and it prevents inherited prototype state from participating in Pack validation.

## Privacy/error posture

Nested Pack validation failures are normalized to the manifest index and do not echo arbitrary rejected property names or Pack/customer content through Registry errors.

JSON parse errors are generic. Exact lookup queries are data-only primitive strings and are never interpreted as URLs, paths, selectors, regexes, or executable expressions.

## Package boundary

```text
experience-registry -> experience-packs
```

No other internal production dependency is permitted.

## Explicit non-goals

Do not:

- store artifact bytes;
- add filesystem/database/object-store access;
- add OCI/ORAS network transport;
- create registry HTTP endpoints;
- invent a second Pack digest/media type;
- resolve mutable tags such as `latest`;
- implement marketplace search/ranking/reviews;
- add publisher authentication or signing;
- depend on Studio runtime, React/Puck, Policy Engine, Observability, Marketplace, or Protocol Gateway.

OCI Distribution remains a possible later transport because it standardizes push/pull/content discovery for manifests and blobs, but it is not the canonical Vira Registry model in REG-001.

## Acceptance direction

1. exact canonical Pack parser delegation;
2. no copied Pack field validation;
3. deterministic immutable snapshot;
4. duplicate id/version rejection;
5. exact lookup hit and miss;
6. malformed Pack remains an error, never a Registry entry;
7. arbitrary object/Proxy input rejected before reflection;
8. bounded serialized ingress before JSON parsing;
9. parsed JSON object prototypes detached before Pack validation;
10. canonical snapshot identity required for lookup;
11. lookup safety bound independent from Pack syntax limits;
12. nested validation errors sanitized;
13. dependency boundary only to `experience-packs`;
14. architecture/security second RE;
15. local repository CI deferred to the final all-phase gate per user instruction.

No merge until the final all-phase integration has passed local CI on reconciled heads and final reverse-engineering verdict is `PASS`.
