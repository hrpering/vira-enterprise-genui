## Reverse-engineering baseline

The repository already owns:

- canonical Vira data/protocol primitives in `@vira-enterprise-genui/protocol`;
- canonical external tool-result contract in `@vira-enterprise-genui/tool-bridge`;
- MCP `CallToolResult` normalization in tool-bridge;
- LangChain `ToolMessage` normalization in tool-bridge.

Both existing provider adapters already delegate structured data through canonical protocol JSON validation and finish through `parseExternalToolResult()`.

Therefore Protocol Gateway must not parse MCP or LangChain wire schemas itself and must not create a replacement Vira protocol.

## Goal

Add one provider-neutral dispatch boundary for external tool-result protocols already supported by tool-bridge.

```text
external provider result
       ↓
Protocol Gateway
       ↓
closed protocol dispatch
       ├─ mcp       → existing normalizeMcpCallToolResult()
       └─ langchain → existing normalizeLangChainToolMessage()
       ↓
existing canonical ExternalToolResult
```

## V1 wrapper

Input fields:

- `protocol`: `mcp` or `langchain`;
- `toolName`: canonical tool semantic name delegated to the provider normalizer;
- `payload`: provider-native result/message value.

Successful output is the existing canonical `ExternalToolResult` with no Gateway-specific envelope.

## Error normalization

Gateway wrapper validation is fail closed and does not echo arbitrary rejected property names.

Provider adapter failures are normalized to fixed Gateway paths:

- invalid tool name → `$.toolName`;
- canonical result rejection → `$.payload` with a dedicated code;
- other provider-result failures → `$.payload`.

Provider-specific dynamic validation paths/messages are not promoted into the Gateway API.

## Explicit non-goals

Do not:

- reimplement MCP `CallToolResult` parsing;
- reimplement LangChain `ToolMessage` parsing;
- add JSON-RPC, SSE, HTTP, WebSocket, session or transport handling;
- add MCP server/client lifecycle;
- add provider discovery or tool invocation;
- add OpenAI/Anthropic/A2A adapters without an owning normalization adapter;
- create a new canonical tool-result or protocol schema;
- add arbitrary provider metadata/context bags to Gateway output;
- depend on runtime/UI/Studio/Registry/Marketplace/Policy/Observability packages.

## Current ecosystem check

Current MCP schemas continue to expose `content`, optional `structuredContent`, and optional `isError` for tool results, while newer SDK revisions add wire-era fields. This reinforces that wire compatibility belongs inside the MCP adapter, not in the Gateway dispatcher.

LangChain ToolMessage continues to expose structured `artifact` data separately from model-facing content. Existing tool-bridge normalization already owns that mapping.

## Package boundary

```text
protocol-gateway -> tool-bridge
```

No direct production dependency on `protocol` is needed because tool-bridge remains the canonical provider-normalization owner.

## Acceptance direction

1. exact dispatch parity with existing MCP normalizer;
2. exact dispatch parity with existing LangChain normalizer;
3. successful output is canonical `ExternalToolResult`, not a Gateway copy;
4. unsupported protocols fail closed;
5. unknown wrapper fields fail closed without reflecting their names;
6. wrapper accessors/symbols rejected without getter execution;
7. provider errors normalized without provider payload/path leakage;
8. no transport/tool execution surface;
9. dependency boundary only to `tool-bridge`;
10. architecture/security second RE;
11. local repository CI deferred to the final all-phase gate per user instruction.

No merge until the final all-phase integration has passed local CI on reconciled heads and final reverse-engineering verdict is `PASS`.
