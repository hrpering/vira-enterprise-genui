# PR-064: Runtime Web Capability Security Gate

## Goal
Make capability allowlisting an enforced Runtime Web mount invariant rather than a standalone security utility: every render capability must be explicitly authorized before the DOM Port is touched.

## Scope
- Add `@vira-enterprise-genui/security` as an allowed Runtime Web package dependency.
- Make `capabilityAllowlist` a required public Web SDK configuration field.
- Normalize/snapshot the allowlist during SDK configuration.
- Revalidate the allowlist at the direct `mountExperience` boundary.
- Evaluate every canonical RenderModel binding using Security's exact allowlist owner.
- Abort the entire mount on the first denied capability; do not prune/partially render.
- Return a distinct `CAPABILITY_DENIED` mount error.
- Run capability authorization before container measurement / DOM begin / component mount.
- Keep Runtime Core action permission policy separate from render capability authorization.
- Migrate existing Runtime Web/Web Component/React fixtures to explicit capability policies.
- Add security integration tests and documentation.

## Explicitly out of scope
- deriving authorization from Component Adapter mappings.
- implicit allow-all defaults.
- wildcard/prefix/fuzzy capability matching.
- Runtime Core action permission changes.
- role/claim/tenant authorization.
- network policy enforcement.
- silently dropping unauthorized regions/components.

## Acceptance criteria
- missing/invalid SDK capability allowlist fails configuration.
- caller mutation after configuration cannot change the normalized allowlist.
- direct mount revalidates policy and fails closed.
- component mapping alone does not authorize a capability.
- empty allowlist denies a valid render capability.
- a single denied capability aborts the whole mount before any DOM Port method, including measurement.
- allowed capabilities mount with existing deterministic order/rollback behavior unchanged.
- SDK surfaces capability denial distinctly from invalid render input and DOM host failure.
- Security owns exact membership logic; Runtime Web does not duplicate matching rules.

## RE/QC focus
Look for implicit allow defaults, component-mapping-as-permission, partial rendering, authorization after DOM access, duplicated matching logic, action-permission conflation, stale caller-policy references, denial remapped to DOM failure, hidden wildcard behavior, or security checks only in the SDK but bypassable through direct mount.
