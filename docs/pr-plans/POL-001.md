# POL-001 — Policy Engine decision boundary

## Status

Planned from authoritative `main` `5266db3e56f4c3e2de4a91f3dcb70e3108dbd2d4`.

Branch: `feat/policy-engine-v1`.

This work is independent from the open Experience Observability PR and must not import from any unmerged branch. Before final local CI it must be reconciled onto the then-latest authoritative main.

## Reverse-engineering baseline

The repository already owns enforcement-oriented security policies in `@vira-enterprise-genui/security`:

- capability allowlist policy + `evaluateCapabilityAllowlist()`;
- component allowlist policy + `evaluateComponentAllowlist()`;
- network policy + `evaluateNetworkRequest()`;
- content and CSP security surfaces.

The existing capability/component/network evaluators already own their policy syntax, validation, request/key validation, fail-closed behavior, and allow/deny semantics.

Therefore Policy Engine must not introduce replacement capability/component/network rule schemas and must not become a second security package.

## Goal

Create a provider-neutral decision layer that gives callers one bounded Vira policy-check boundary while delegating domain evaluation to the existing security owners.

```text
policy check request
        ↓
@vira-enterprise-genui/policy-engine
        ↓
closed check-kind routing
        ↓
existing @vira-enterprise-genui/security evaluator
        ↓
normalized Vira policy decision
        ↓
existing runtime/security enforcement
```

Policy Engine decides; it does not perform the protected action and does not replace enforcement.

## V1 candidate check kinds

Only existing security-owned domains may be normalized in v1:

- `capability` → existing capability allowlist evaluator;
- `component` → existing component allowlist evaluator;
- `network` → existing network request evaluator.

The implementation must reuse the existing security policy types/evaluators rather than copy their validation logic.

Content/CSP policy routing is out of scope until reverse engineering proves a stable allow/deny evaluator contract analogous to the three domains above.

## Decision semantics

The normalized success surface should remain intentionally small:

- check kind;
- `allow` or `deny`;
- no arbitrary metadata/context bag;
- no customer/user/tenant identifiers;
- no raw request/policy echo unless a canonical security type explicitly requires it.

Malformed policy/check input must remain distinguishable from a valid `deny` result. Policy Engine must not silently translate invalid configuration into a normal business denial and thereby hide operational/configuration errors. Enforcement callers remain responsible for treating non-success evaluation as fail-closed.

## Explicit non-goals

Do not:

- invent a general-purpose rule language or expression evaluator;
- add arbitrary JavaScript/JSONLogic/Rego execution to core;
- replace existing security policy contracts;
- duplicate network/capability/component validation;
- add RBAC/ABAC identity models before canonical identity contracts exist;
- add tenant/user/session/profile attributes;
- add policy persistence, admin UI, database, network service or remote policy fetch;
- make OPA a production dependency;
- execute protected actions;
- couple Policy Engine to Experience Packs, Observability, Registry, Marketplace, Studio/Puck, React or runtime UI packages.

OPA/Rego may later be a replaceable adapter/provider only if a future external-policy requirement exists. Vira canonical policy checks must remain provider-neutral.

## Intended package boundary

```text
policy-engine -> security
```

No other internal production dependency is intended for POL-001.

## Security invariants

- closed check-kind allowlist;
- strict plain-data inspection;
- unknown fields fail closed;
- no accessors/symbol-backed input execution;
- no arbitrary attributes or raw customer content;
- underlying security evaluator errors are preserved/normalized without leaking policy content;
- a valid `deny` must not be confused with invalid policy configuration;
- no policy-engine path may bypass existing runtime/security enforcement.

## Acceptance direction

Before implementation is considered complete:

1. characterize all three existing security evaluators and their error/decision contracts;
2. prove Policy Engine delegates rather than reimplements them;
3. exact parity tests for capability/component/network allow and deny;
4. malformed policy/request parity tests;
5. fail-closed unknown/accessor/symbol input tests;
6. no customer-content or identifier surface;
7. dependency boundary only to `security`;
8. architecture/security second RE;
9. repository local CI on exact final head;
10. latest-main reconciliation and final squash-merge gate.

## Merge rule

No merge until implementation has a final user-run local CI PASS on the exact final head and final reverse-engineering verdict `PASS`.
