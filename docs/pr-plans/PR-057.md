# PR-057: Deterministic Tool Freshness Evaluation

## Goal
Classify provider-neutral tool-result freshness with an explicit caller-supplied clock, without introducing hidden wall-clock reads, retry/cache policy, or transport behavior.

## Scope
- Add deterministic freshness statuses: `unknown`, `future`, `fresh`, `stale`.
- Add `evaluateToolResultFreshness(result, nowUnixMs)`.
- Reuse the existing `ExternalToolResult` parser before freshness evaluation.
- Require `nowUnixMs` to be a non-negative safe integer.
- Treat missing freshness as `unknown`.
- Treat `nowUnixMs < observedAtUnixMs` as `future`.
- Treat `nowUnixMs >= expiresAtUnixMs` as `stale` when expiry exists.
- Treat remaining observations as `fresh`.
- Return detached immutable evaluation metadata.
- Add deterministic boundary tests and documentation.

## Explicitly out of scope
- `Date.now()` or any hidden clock.
- retry, cache eviction, refresh, or rejection policy.
- clock-skew tolerance.
- network/tool execution.
- provider-specific timestamp parsing.
- mutation of DomainData or ExternalToolResult.

## Acceptance criteria
- Same result + same `nowUnixMs` always yields the same classification.
- No runtime/global clock is read.
- Invalid tool results fail through the owning ExternalToolResult parser boundary.
- Invalid caller clock fails before freshness classification.
- `expiresAtUnixMs` is stale at the exact expiry boundary.
- Missing expiry remains fresh after observation unless policy elsewhere decides otherwise.
- Missing freshness is `unknown`, not fabricated from the caller clock.

## RE/QC focus
Look for hidden `Date.now()` usage, retry/cache policy disguised as classification, mutation of the parsed result, non-deterministic boundaries, stale/future ambiguity, invented timestamps, provider assumptions, or direct Runtime Web/Adapter SDK coupling.
