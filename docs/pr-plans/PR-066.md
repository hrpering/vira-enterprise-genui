# PR-066: Runtime Web Component Security Gate

## Goal
Enforce exact component authorization at Runtime Web mount time in addition to the existing capability gate, before any DOM Port side effect.

## Scope
- Make `componentAllowlist` a required public Web SDK configuration field.
- Normalize/snapshot the component policy during SDK configuration.
- Require/revalidate `componentAllowlist` at direct `mountExperience()` boundary.
- Preserve fixed gate order: RenderModel integrity -> capability authorization -> component authorization -> responsive/DOM.
- Evaluate exact `binding.component` through Security's component allowlist owner.
- Abort the full mount on first denied component; no partial render.
- Add `INVALID_COMPONENT_ALLOWLIST` and `COMPONENT_DENIED` outcomes.
- Surface component denial distinctly through the public SDK.
- Migrate existing Runtime Web, React, Web Component, and golden fixtures to explicit component policies.
- Add dedicated contract tests and documentation.

## Explicitly out of scope
- deriving component permission from Component Adapter mappings.
- wildcard/prefix/suffix/regex/fuzzy matching.
- changing component semantic validation ownership.
- changing capability authorization semantics.
- changing Runtime Core action permissions.
- customer role/tenant authorization.
- network policy enforcement.
- partial rendering of permitted subsets.

## Acceptance criteria
- missing/invalid SDK component allowlist fails configuration.
- direct mount revalidates the policy.
- caller mutation after configuration cannot change the normalized policy.
- valid component mapping without explicit component permission denies.
- one denied component aborts before container measurement / DOM begin / mount.
- all capabilities and components allowed preserves existing deterministic mount behavior.
- if both capability and component would deny, capability gate wins deterministically.
- SDK surfaces `COMPONENT_DENIED` distinctly.
- capability, component, and action permission responsibilities remain separate.

## RE/QC focus
Look for component-mapping-as-permission, implicit allow defaults, partial rendering, component checks after DOM access, duplicated matching logic, policy mutation, direct-mount bypass, capability/component conflation, action permission conflation, denial remapped to generic DOM failure, or framework/customer-specific assumptions.
