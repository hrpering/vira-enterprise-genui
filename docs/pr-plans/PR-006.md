# PR-006: Capability Protocol v1

## Goal
Define the minimal semantic capability identity used by planners and adapters without introducing component concepts.

## Scope
- Define versioned `Capability` with one semantic `id`.
- Reuse the shared semantic namespace grammar.
- Reject unknown/presentational/implementation fields.
- Add runtime parsing, a golden fixture, contract tests, and documentation.

## Out of scope
- Component registry or adapter mapping.
- Capability parameters/props.
- Planner capability resolution.
- Actions, permissions, layout, rendering, or domain execution.
- Capability sets inside ExperiencePlan.

## Allowed files
- `packages/protocol/src/capability/**`
- `packages/protocol/src/index.ts`
- `tests/contract/capability.test.ts`
- `tests/fixtures/protocol/capability.v1.json`
- `docs/protocol/capability.md`
- `docs/pr-plans/PR-006.md`

## Acceptance criteria
- Valid simple and namespaced capability IDs parse deterministically.
- Invalid/unsupported IDs and versions fail with typed issues.
- Unknown fields such as `component` and `props` are rejected.
- Accessor fields are rejected without intentionally invoking getters on normal objects.
- Capability remains framework-, brand-, domain-, and transport-neutral.
- Protocol code performs no filesystem/network access.

## RE/QC focus
Confirm capability remains semantic identity only. Look for component/config/props creep, domain coupling, executable data, adapter responsibility leakage, and duplicated identifier rules.
